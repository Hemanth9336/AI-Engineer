The API is strict about the shape of the history. Knowing exactly what each turn appends - and the rules that tie messages together - lets you build, repair and shrink histories without breaking them.

## Turn by turn

| Event | Append | Rule |
|---|---|---|
| Start | `system`, then `user` | System first; the task as the first user message |
| Model asks for tools | one `assistant` with `tool_calls: [{id, function}]` | Append it **before** any results |
| Each tool runs | one `tool` per call, with `tool_call_id` | Every call id answered exactly once, right after its assistant message |
| Model answers | one `assistant` with `content` | No tool calls |
| User follows up | one `user` | Only after all tool calls are answered |

```text
[0] system     You are Stackline's project assistant...
[1] user       Compare the ports of billing and search.
[2] assistant  tool_calls: call_1 list_dir(services)
[3] tool       call_1 -> billing.yaml / search.yaml
[4] assistant  tool_calls: call_2 read_file(billing.yaml), call_3 read_file(search.yaml)
[5] tool       call_2 -> name: billing / port: 8081 ...
[6] tool       call_3 -> name: search / port: 9200 ...
[7] assistant  Billing uses 8081 and search uses 9200.
```

Two calls in one assistant message (`[4]`) means two tool messages in a row (`[5]`, `[6]`), in any order - but both before anything else.

## How histories break

| Bug | Typical cause | What happens |
|---|---|---|
| Tool result before its call | appended results, then the assistant message | Request rejected |
| Wrong `tool_call_id` | copy-paste, or ids generated by your code | Rejected, or the result is matched to the wrong call |
| Missing result for one call | an exception skipped the append | Rejected: "tool_calls must be followed by tool messages" |
| Result appended twice | retry logic that appends on each attempt | Rejected, or a confused model |
| Compaction cut between a call and its result | naive "keep the last N messages" | Rejected |

The last one is a trap you'll meet again in topic 18: when you drop old messages, drop **whole turns** - an assistant message together with all of its tool results.

## Repairing a broken history

If a crash left the history broken, you don't have to start over:

1. **Reorder** so each assistant tool-call message comes before its results.
2. **Fix ids** so every result answers a real call.
3. **Fill gaps** - re-run the missing tool call (if it's safe and read-only), or insert an honest `error: result lost, call again if needed`.
4. **Validate** before sending: every call answered once, no orphan results.

You'll do exactly this by hand in the next task.
